# Code Execution Security

`src/evaluation/sandbox/executor.py` runs **untrusted, model-generated code**
(Python scripts, and C/C++ source that it compiles and then runs) via
`subprocess`. This document is the single source of truth for the risk, the
controls, and what an operator must do before turning this feature on
anywhere near production.

## The risk

The code executed here is not written or reviewed by anyone on this team --
it is generated by an LLM as part of the HumanEval/MBPP-style benchmark
pipeline (`src/evaluation/pipeline/benchmark_runner.py`). Treat it exactly
like you would treat code from an anonymous internet submission:

- It can attempt to read/exfiltrate any file the process can see (secrets,
  other tenants' data, source code).
- It can attempt to reach the network (call out to an attacker-controlled
  host, scan the internal network, hit cloud metadata endpoints).
- It can attempt to exhaust CPU, memory, disk, or process-table resources
  (denial of service against the host).
- It can attempt privilege escalation or container/VM escape if the host is
  not otherwise hardened.

## Defense-in-depth layers

Two independent layers exist. **Neither is optional context for the other —
both apply whenever code execution is enabled.**

### 1. Process-level mitigations (always applied when enabled)

Applied by `executor.py` regardless of sandbox backend:

- A scrubbed subprocess environment (`_scrubbed_subprocess_env`): only
  `PATH`, `HOME`, `LANG`, `LC_ALL` are forwarded. Secrets such as
  `GEMINI_API_KEYS` are never visible to the child process.
- Best-effort POSIX rlimits via `preexec_fn`: CPU time
  (`sandbox_cpu_seconds`), address space (`sandbox_memory_bytes`), process
  count (`sandbox_max_processes`, sized relative to ambient load), and max
  file size (`sandbox_max_file_size_bytes`).

These mitigations reduce blast radius but provide **no real isolation** --
there is no network restriction, no filesystem restriction, and no
namespace/user separation from the host.

### 2. OS-level sandbox backend (opt-in, `EVAL_SANDBOX_BACKEND`)

Set via `EVAL_SANDBOX_BACKEND` (or `sandbox_backend` in
`src/evaluation/config/settings.py`), one of:

| Value | Behavior |
|---|---|
| `none` (default) | No OS isolation. Rlimits/env-scrubbing only (layer 1). A `SECURITY` warning is logged on every execution while this is active. **Must not be used in production.** |
| `bubblewrap` | Wraps the child command with `bwrap`: all namespaces unshared (no network, own PID/mount/UTS/IPC namespace), base OS (`/usr`, `/lib`, `/lib64`, `/bin`, `/etc`, ...) mounted read-only, a fresh `tmpfs` at `/tmp`, and the per-execution work directory as the only read-write bind. |
| `nsjail` | Equivalent isolation via `nsjail` (`-Mo --disable_proc --iface_no_lo --chroot / --cwd <workdir> --bindmount <workdir>:<workdir> ...`). Treat the exact flags as a starting template -- validate them against the `nsjail` version and kernel actually deployed before relying on this backend. |

Optional `EVAL_SANDBOX_WRAPPER_PATH` overrides the wrapper executable's
location; otherwise it is resolved from `PATH` via the backend's
conventional binary name (`bwrap`, `nsjail`).

### Fail-closed behavior

If `EVAL_SANDBOX_BACKEND` is set to `bubblewrap` or `nsjail` but the
corresponding executable cannot be found (`EVAL_SANDBOX_WRAPPER_PATH`, or a
`PATH` lookup, both come up empty), the executor **refuses to run the code
at all**. It returns the same `status: "disabled"` result shape used when
`EVAL_ENABLE_CODE_EXECUTION` is off, with an explanatory `stderr` message,
and logs an error. It never silently falls back to running the command
unsandboxed. This check happens once per request in
`ExecutionSandbox._resolve_sandbox_wrapper`, before any workdir/subprocess
work begins.

## Feature flags

| Flag | Env var | Default | Purpose |
|---|---|---|---|
| `enable_code_execution` | `EVAL_ENABLE_CODE_EXECUTION` | `false` | Master switch. When `false`, `execute()` returns `status: "disabled"` immediately and nothing runs. |
| `sandbox_backend` | `EVAL_SANDBOX_BACKEND` | `none` | OS isolation backend: `none` \| `bubblewrap` \| `nsjail`. |
| `sandbox_wrapper_path` | `EVAL_SANDBOX_WRAPPER_PATH` | unset | Explicit path to the `bwrap`/`nsjail` binary, overriding the `PATH` lookup. |
| `sandbox_cpu_seconds`, `sandbox_memory_bytes`, `sandbox_max_processes`, `sandbox_max_file_size_bytes` | `EVAL_SANDBOX_*` | see `settings.py` | Layer-1 rlimits, applied inside the sandbox too as defense-in-depth. |

## Installing a sandbox backend

### bubblewrap (`bwrap`)

Recommended when the AI service runs on/as a Linux container host with user
namespaces available.

```bash
# Debian/Ubuntu
sudo apt-get install -y bubblewrap

# Alpine
apk add bubblewrap

# Fedora/RHEL
sudo dnf install -y bubblewrap
```

Verify: `bwrap --version`. If the AI service itself runs inside a Docker
container, that container needs `CAP_SYS_ADMIN` (or run privileged) and
access to user namespaces for `bwrap --unshare-all` to succeed -- see the
Kubernetes/Docker section below for the trade-offs.

### nsjail

```bash
# Build from source (no prebuilt packages on most distros)
git clone https://github.com/google/nsjail.git
cd nsjail && make
sudo install -m 0755 nsjail /usr/local/bin/nsjail
```

Verify: `nsjail --help`. Validate the exact flag set in
`_nsjail_command` (`src/evaluation/sandbox/executor.py`) against your
kernel/nsjail version in a staging environment before enabling in
production -- nsjail's namespace/seccomp flags vary across versions.

## Hardened deployment (Docker / Kubernetes)

Whichever backend you choose, treat the **container/pod running the AI
service** as a second, coarser isolation boundary around the sandbox
process itself:

- **Network**: `docker run --network none` (or a Kubernetes
  `NetworkPolicy` that denies all egress/ingress for this workload). The
  code executor has no legitimate reason to reach the network.
- **Read-only rootfs**: `docker run --read-only` (Kubernetes:
  `securityContext.readOnlyRootFilesystem: true`), with an explicit
  writable `tmpfs` mount only for the executor's `temp_root`
  (`data-source/evaluation/tmp` by default).
- **Non-root user**: `docker run --user <uid>:<gid>` (Kubernetes:
  `securityContext.runAsNonRoot: true`, `runAsUser: <uid>`). Never run the
  executor as root.
- **Seccomp**: apply a restrictive seccomp profile (`--security-opt
  seccomp=<profile>.json` / Kubernetes `securityContext.seccompProfile`)
  that denies namespace/mount/ptrace syscalls beyond what `bwrap`/`nsjail`
  themselves need.
- **PID limit**: `docker run --pids-limit=<n>` (Kubernetes:
  `resources.limits` combined with a `PodSecurityPolicy`/cgroup PID
  limit) as a hard backstop above the process-level `RLIMIT_NPROC`.
- **Memory/CPU limits**: `docker run --memory=<n> --cpus=<n>` (Kubernetes
  `resources.limits.memory` / `resources.limits.cpu`) as a hard backstop
  above `sandbox_memory_bytes` / `sandbox_cpu_seconds`.
- **Capabilities**: drop all Linux capabilities (`--cap-drop=ALL`) and add
  back only what the chosen sandbox backend needs to create namespaces
  (typically `CAP_SYS_ADMIN` for `bwrap`, or run in a context where user
  namespaces are unprivileged).

## Explicit operating rule

**Code execution must remain disabled (`EVAL_ENABLE_CODE_EXECUTION=false`,
the default) in any shared, staging, or production environment until:**

1. A sandbox backend (`bubblewrap` or `nsjail`) is installed and configured
   via `EVAL_SANDBOX_BACKEND`, and
2. The hardened deployment controls above (no network, read-only rootfs,
   non-root user, seccomp, pid/memory/cpu limits) are in place for the
   container/pod running the AI service, and
3. Both have been verified end-to-end in a non-production environment --
   confirm the executor actually refuses to run (fail-closed) when the
   configured backend's binary is temporarily removed, and confirm a
   deliberately malicious sample (e.g. attempting outbound network access
   or reading `/etc/shadow`) is blocked when the backend is present.

Running with `EVAL_SANDBOX_BACKEND=none` outside of local development is a
production security incident waiting to happen, not a configuration choice.
